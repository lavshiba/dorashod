Перед работой обязательно прочитать:

- `README.md`
- `AGENTS.md`
- `docs/product-spec.md`
- `docs/architecture.md`
- `docs/operations.md`
- `docs/testing.md`
- `PLANS.md`

Эти файлы считаются repo-level памятью проекта и главным source of truth по текущему состоянию.

## Критическое правило по пользовательским текстам

Пользовательские тексты, подписи, заголовки экранов, описания, статусы, словарь и названия кнопок из ТЗ считаются зафиксированными source of truth.

Дополнительный внешний source of truth по текстам интерфейса:

- `/home/abihsgelo/.var/app/org.telegram.desktop/data/TelegramDesktop/tdata/temp_data/codex_ui_texts_package/frozen_ui_texts_for_codex.txt`

Если тексты в репозитории расходятся с этим файлом, приоритет у этого файла, пока пользователь явно не заменит его новой версией.

Запрещено:

- переписывать тексты “как будет лучше”
- сокращать формулировки по своему вкусу
- заменять слова синонимами
- менять названия кнопок
- менять порядок элементов на экранах
- заменять согласованные формулировки на свои варианты

Если в ТЗ указано конкретное название кнопки, текст экрана, формулировка статуса или словарь, нужно использовать именно это.

Обязательная проверка перед завершением каждой значимой задачи:

- совпадают ли названия кнопок с ТЗ
- совпадают ли заголовки экранов с ТЗ
- совпадают ли поясняющие тексты с ТЗ
- совпадает ли словарь действий и сущностей с ТЗ
- не появились ли самовольные замены слов

Если есть расхождение, задача не завершена.

## Архитектурные правила проекта

- Хостинг: GitHub + Cloudflare Workers + Cloudflare D1.
- Telegram updates принимаются только через webhook.
- Периодические проверки и фоновые задачи делаются только через Cloudflare Cron Triggers.
- Основной storage: D1.
- Секреты нельзя хранить в git, коде или документации.
- Нужно проектировать под free-план Cloudflare и экономить запросы.
- Все значимые изменения сопровождаются обновлением документации.

## Правила поддержки через Codex

- По умолчанию считать, что все будущие изменения делает только Codex.
- После изменения логики, архитектуры, деплоя, команд, схемы данных или пользовательских сценариев обновлять `README.md` и `docs/*`.
- После изменения repo-level правил обновлять `AGENTS.md`.
- После изменения roadmap, крупных задач или статуса работ обновлять `PLANS.md`.

## Правила деплоя и проверки

- Не считать задачу завершённой без прогонов `lint`, `build`, `test`.
- Перед прод-деплоем проверять миграции.
- После прод-деплоя выполнять post-deploy checks.
- Если что-то не удалось проверить автоматически, честно фиксировать это в отчёте и в документации, когда это влияет на проект.
