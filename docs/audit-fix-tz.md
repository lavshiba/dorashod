# ТЗ: аудит и исправление проекта dorashod

## Статус

Рабочее ТЗ на полный аудит и исправление текущего состояния проекта `dorashod`.

## Цель

Привести код, документацию, тесты, деплойный сценарий и пользовательские тексты проекта к одному проверяемому состоянию без внешних локальных source of truth и без ложных claims о реализованной функциональности.

## Входные source of truth

Обязательные источники для выполнения работ:

- `README.md`
- `AGENTS.md`
- `docs/product-spec.md`
- `docs/architecture.md`
- `docs/operations.md`
- `docs/testing.md`
- `PLANS.md`
- repo-local frozen source of truth: `docs/frozen/ui-texts.txt`
- исходный аудит-заказ, перенесённый в этот документ

Результат работ обязан держать source of truth внутри репозитория и не зависеть от абсолютных локальных путей.

## Принципы выполнения

- Ничего не исправлять "на глаз": сначала сверять код, документацию, тесты и пользовательские тексты.
- Пользовательские тексты, названия кнопок, экранов, статусов и словарь не переписывать своими словами.
- Любое расхождение между кодом и согласованными текстами исправлять в пользу frozen source of truth.
- Не оставлять в документации claims о функциональности, если она не реализована и не проверена.
- Все значимые изменения сопровождать обновлением документации.
- Не считать задачу завершённой без `lint`, `build`, `test`.

## Обязательный результат

После выполнения этого ТЗ репозиторий должен:

- содержать repo-local frozen source of truth по пользовательским текстам и логике интерфейса;
- быть пригодным для повторного внешнего аудита по GitHub без доступа к локальной машине;
- не ссылаться в README и product-spec на локальные абсолютные пути;
- иметь документацию, соответствующую реальному состоянию кода;
- иметь автоматические проверки для ключевых исправлений;
- иметь честный и воспроизводимый деплойный и post-deploy сценарий.

## Область работ

### 1. Repo-local source of truth по текстам

Нужно:

- убрать зависимость от внешнего frozen-файла по локальному пути;
- создать repo-local файл с замороженными текстами экранов, кнопок, словаря и правил навигации;
- сделать этот файл обычным файлом внутри репозитория, пригодным для GitHub-ссылки и raw-ссылки;
- перевести `README.md`, `docs/product-spec.md` и кодовые ссылки на repo-local source of truth;
- проверить, что пользовательские тексты в коде не разъехались с frozen-версией.

Критерии приёмки:

- в репозитории есть один явный основной frozen-файл;
- в `README.md` и `docs/product-spec.md` больше нет ссылок на локальные абсолютные пути;
- в коде и тестах ссылки на тексты используют repo-local источник;
- frozen-файл включает:
  - словарь кнопок;
  - словарь сущностей;
  - замороженные тексты ключевых экранов;
  - правила навигации.

### 2. Ветка `данные -> в другие приложения`

Нужно:

- исправить экспорт так, чтобы он формировал реальный CSV, а не JSON;
- привести формат к согласованной структуре:
  - `date`
  - `time`
  - `amount`
  - `type`
  - `category`
  - `subcategory`
  - `description`
- выдавать файл с CSV-расширением и корректным именем;
- убрать ложные пользовательские формулировки, если интерфейс обещает таблицу, а отдаёт не таблицу;
- сохранить рабочий импорт из CSV.

Критерии приёмки:

- экспортируемый файл открывается как CSV;
- заголовки и порядок колонок совпадают с ТЗ;
- импорт принимает CSV, сформированный этим же экспортом;
- round-trip `экспорт -> импорт` сохраняет данные в ожидаемом объёме.

### 3. `очистить всё`

Нужно:

- привести поведение к тексту экрана и ТЗ;
- после `очистить всё` реально возвращать пользователя к начальному состоянию;
- очищать:
  - записи;
  - категории;
  - подкатегории;
  - настройки;
  - черновик;
  - новые записи.

Критерии приёмки:

- код удаляет или сбрасывает все перечисленные сущности;
- пользователь после действия видит состояние, соответствующее пустому начальному сценарию;
- добавлены автоматические тесты на этот сценарий.

### 4. Cron-слой

Нужно выбрать один из двух честных вариантов:

1. реализовать реальные полезные cron-задачи, соответствующие текущему продукту;
2. убрать ложные claims из README, `docs/*`, конфигурации и тестов, если cron-логика фактически пустая.

Запрещено оставлять заглушку, которая создаёт видимость готовой cron-функциональности.

Критерии приёмки:

- `runCron()` либо выполняет полезную проверяемую работу, либо cron-слой упрощён и задокументирован честно;
- тесты и документация совпадают с фактическим поведением;
- `wrangler.jsonc` не обещает лишнего.

### 5. Автоматизация деплоя и post-deploy

Нужно:

- довести post-deploy checks до автоматического запуска после деплоя;
- автоматизировать установку или проверку webhook;
- если установка webhook не может быть полностью автоматической без секрета, сделать явный отдельный шаг или скрипт и задокументировать это;
- добиться, чтобы workflow честно проверял, что production после деплоя жив.

Критерии приёмки:

- после деплоя запускается post-deploy smoke;
- есть воспроизводимый способ проверить или установить webhook;
- документация явно разделяет автоматические шаги и ручные шаги с секретами;
- production health проверяется автоматически или вынесен честный ручной шаг с причиной.

### 6. README

Нужно полностью переписать `README.md` в операторский readme без локальных путей и без длинной ленты change-log в начале.

Обязательная структура:

- что это за бот;
- что умеет;
- стек;
- инфраструктура;
- как запускать;
- как деплоить;
- как обновлять;
- как проверять;
- как восстанавливать;
- ограничения free-плана.

Если исторический changelog нужен, он должен жить отдельно, а не в начале README.

### 7. `docs/product-spec.md`

Нужно:

- превратить документ в полноценный product spec;
- перенести туда актуальный словарь, frozen-кнопки и frozen-экраны;
- сделать явную ссылку на repo-local frozen source of truth;
- убрать зависимость от внешнего локального файла.

Критерии приёмки:

- `docs/product-spec.md` можно читать как самодостаточное описание продукта;
- в нём есть актуальная продуктовая логика, а не короткая заглушка;
- frozen-материалы находятся в репозитории.

### 8. `docs/architecture.md`

Нужно:

- привести документ к реальной структуре проекта;
- убрать ссылки на несуществующие слои и каталоги;
- описать фактический layout исходников, данных, runtime-входов и bindings.

Критерии приёмки:

- перечисленные директории и слои реально существуют;
- схема данных и runtime entrypoints совпадают с кодом.

### 9. `docs/operations.md`

Нужно:

- убрать локальные абсолютные пути;
- исправить пример webhook URL;
- проверить применимость всех команд и шагов;
- явно разделить:
  - что делается автоматически;
  - что делается вручную;
  - что требует секретов.

Критерии приёмки:

- документ применим к чистому окружению без догадок;
- в нём нет битых примеров и устаревших шагов.

### 10. Тестовое покрытие

Нужно добавить или обновить тесты на:

- `очистить всё`;
- экспорт CSV;
- импорт CSV после экспорта;
- ключевые frozen-тексты экранов, а не только несколько кнопок;
- cron-логику, если она остаётся в продукте;
- post-deploy smoke или честную фиксацию, почему часть проверки не автоматизирована.

Критерии приёмки:

- тесты падают на старом дефектном поведении и проходят после исправления;
- ключевые claims документации подтверждены тестами или явно помечены как ручные.

### 11. `BACKUP_SIGNING_KEY`

Нужно разобраться с обязательным секретом `BACKUP_SIGNING_KEY`.

Допустимы только два результата:

1. секрет реально используется, и это отражено в коде, env schema, bindings и документации;
2. секрет не нужен, и тогда он удалён из env schema, конфигурации, документации и примеров.

Запрещено оставлять мёртвый обязательный секрет.

### 12. Финальная верификация

После выполнения всех исправлений обязательно выполнить:

- `npm run lint`
- `npm run build`
- `npm run test`
- локальные проверки, связанные с миграциями и сценариями данных;
- проверку деплойного сценария;
- post-deploy checks;
- сверку документации с фактическим состоянием проекта.

Если какой-либо пункт нельзя проверить автоматически, это нужно:

- честно указать в итоговом отчёте;
- отразить в документации, если ограничение влияет на проект.

## Формат итогового отчёта по выполнению

Исполнитель должен в конце работ дать отчёт со следующими блоками:

- что именно было исправлено;
- какие расхождения с ТЗ были найдены;
- что осталось не закрыто;
- какие вещи всё ещё требуют ручного живого прогона в Telegram.

## Definition of Done

Задача считается завершённой только если одновременно выполнено всё ниже:

- frozen source of truth перенесён внутрь репозитория;
- ссылки на локальные абсолютные пути убраны из пользовательской и операторской документации;
- экспорт `в другие приложения` работает как CSV;
- `очистить всё` реально возвращает бота к начальному состоянию;
- cron-слой либо реализован, либо упрощён без ложных claims;
- деплой и post-deploy сценарий воспроизводимы и честно задокументированы;
- README и `docs/*` соответствуют реальному коду;
- `BACKUP_SIGNING_KEY` либо реализован, либо удалён;
- `lint`, `build`, `test` пройдены;
- репозиторий пригоден для повторного внешнего аудита по GitHub-ссылке без доступа к локальной машине.
